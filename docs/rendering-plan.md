# Rendering plan

Decision proposal, researched 2026-09-12. No engine has been installed or selected for production.

Build one isolated **Godot 4 practice-scene spike**, using the Mobile renderer with Metal on the Mac. Keep the current lesson implementation working while this scene proves its geometry, visual quality and timing integration. Pin a released engine version and matching native bindings when the spike starts.

The current AppKit drawing is provisional. Earlier manually projected paths and independently sized shapes produced spatial distortions and overlaps; the native lab is moving to one shared planar projection. The engine spike must preserve that corrected geometry. A 120 Hz `Timer` requests updates; it does not establish 120 rendered or presented frames per second. The next step needs a coherent scene and measurement, not another apparent-frame-rate claim.

| Route | Concrete fit | Decision for this stage |
| --- | --- | --- |
| **Godot 4 + native bridge** | Scene editing, real cameras, materials and native C++ integration. Mobile supports desktop rendering and Metal; Forward+ offers additional effects. | First spike. The restrained practice rail does not yet justify advanced effects. Mobile is a feature-fit choice, not a measured performance win. |
| **Unity 6 + URP + native plug-in** | Complete game scene workflow. Native plug-ins can reuse the existing C/C++ code through C# integration. | Viable fallback if the Godot authoring or packaging experiment fails. Reuse the same scene/timing acceptance criteria instead of restarting the product design. |
| **AppKit shell + MTKView/Metal** | Replaces only the practice view and keeps the present Mac application structure. | Smallest Mac-specific integration, but camera, batching, materials and authoring tools become our responsibility; Windows needs another renderer. Keep as the fallback for a deliberately Mac-only delivery. |

These are engineering judgments. The documented capabilities are [Godot renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html), [Godot C++ extensions](https://docs.godotengine.org/en/stable/tutorials/scripting/cpp/gdextension_cpp_example.html), [Unity URP](https://docs.unity3d.com/6000.0/Documentation/Manual/universal-render-pipeline.html), [Unity native plug-ins](https://docs.unity3d.com/6000.0/Documentation/Manual/plug-ins-native.html), and [MTKView](https://developer.apple.com/documentation/metalkit/mtkview). Engine choice alone does not establish polish or reliability.

The next implementation deliverable should be `spikes/godot-practice/`: one standalone scene, one deterministic replay fixture, one native bridge, and a short capture/report. No course, profiles, sample-library migration or application-shell rewrite belongs in this spike.

1. **Prove the scene first.** Reproduce the approved single planar rail: seven fixed instrument lanes, one NOW line across the whole rail, and full-width kick bars on that same plane. Use one `Camera3D` with restrained perspective, no camera roll, and a shared transform for every vertex of the rail, note meshes and kick bars. Equal-time note centers must have equal screen Y. Reserve a separate static kit reference below NOW; its instruments are decorative references, never timed destinations. Use one authored material palette, clean antialiasing and restrained lighting. Keep note symbols high contrast and readable without bloom, motion blur or camera shake. The camera serves the approved notation rather than introducing a second layout. [Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)
2. **Prove the boundary.** Link the existing C++17 core through a thin GDExtension adapter. Add a small C interface over the Mac device/clock controller rather than porting MIDI or audio to frame callbacks. The current lab still serializes scoring through AppKit's main thread; moving that ownership to one native worker is required before claiming renderer-independent grading. Use bounded commands, timestamped hit events and immutable display snapshots. A visual replay may come first, but label it as replay until the live bridge passes.
3. **Make the first lesson feel finished.** Apply the accepted lesson-room flow to this single scene: hear the groove, play, receive useful feedback, retry. Author the hit response, transitions, type and sound together. Then compare the playable result with the native lab. Expand the engine's ownership only after the gates below pass.

The projection contract must be explicit and testable:

- One aspect-preserving planar camera/view transform owns the rail and every note vertex. Derive note dimensions from their geometry on that plane; do not size note centers, widths, heights or corner radii with unrelated screen-space curves. Keep labels and the static kit reference in the safe region below NOW, clear of controls and feedback.
- Every note uses the same native song time: `remaining = event_time - song_time`. Equal remaining time means equal projected screen Y across all seven lanes and the full-width kick bar, throughout the approach. At zero remaining time every center reaches the same NOW line within one backing pixel. Same-frame arrival alone is insufficient. Do not integrate accumulated frame delta or use instrument-specific paths or speeds.
- Lane positions stay stable across lessons and guidance levels. Kick uses the same plane, progress and projection as hand notes, with no separate foot path, arrival line or timing band. A simultaneous kick and hand chord must remain identifiable without obscuring hand note symbols.
- Check all simultaneous groups, including hi-hat/snare/kick together. At the minimum 1020×780 window size, approaching symbols must remain distinguishable; simplify decoration before changing the shared geometry or shrinking notes into illegible marks. Check the static kit reference below NOW separately from the scored rail.
- Guidance changes visibility only. Hidden notes cannot create connectors or other anticipatory marks. From memory keeps the static rail, NOW line, kit reference and the player's own hit feedback; upcoming notes and beat motion disappear. The existing live-feedback option remains a separate choice.

Native MIDI timestamps, native audio scheduling and the C++ event list remain authoritative. The renderer receives a session/clock generation, host-time anchor, expected events and feedback snapshots. It samples that clock for each frame and applies any measured visual presentation offset only to drawing. It cannot change grades or fire the metronome. Reconnect, sleep/wake and audio-device changes invalidate clock alignment. Godot's audio guidance itself distinguishes mix, device and clock delays; its playback helpers are not a reason to substitute an unrelated engine clock for the existing native one. [Audio synchronization](https://docs.godotengine.org/en/stable/tutorials/audio/sync_with_audio.html)

Before replacing the AppKit view, require the following evidence. These are proposed gates, not current results:

| Gate | Evidence required |
| --- | --- |
| Geometry and legibility | Deterministic images at the current minimum 1020×780 window, 16:9 and 16:10 layouts, including Retina scaling, resize and every chord/guidance state. Equal-time screen-Y checks pass throughout the approach; every note and kick vertex follows the shared transform; all arrivals meet one NOW line within one backing pixel. No unintended overlap with the static kit reference below NOW. Review the moving scene as well as stills. |
| Frame pacing | Packaged build, declared Mac/GPU, pixel resolution, refresh mode and power state. After warm-up, collect ten minutes at 120 Hz: CPU frame work p99 below 4 ms, GPU work p99 below 4 ms, at least 99.9% of presentation intervals within one refresh period plus 1 ms, and none above two periods. Provide a tested 60 Hz mode with corresponding 16.67 ms presentation budget. |
| Timing isolation | Inject deterministic MIDI while deliberately stalling the renderer. Native grades match the replay reference; clicks and demo sample positions remain unchanged; no unreported event loss. Record bounded-queue overflow, sample scheduling and audio-device interruptions. |
| Reliability | Repeat start/stop/retry, lesson changes, device reconnect and sleep/wake. No stale notes or sounds after cancellation. Record any failures and memory growth over a sustained run. |
| Platform decision | Export and inspect the same scene on Windows before committing the production front end. Windows MIDI/audio integration is separate work and requires its own timing measurements. |

Record CPU work, GPU work, queue delay and actual presentation intervals separately. An FPS counter or GPU duration alone cannot establish display latency. Godot's profiler can locate processing costs; platform graphics tooling is still needed to inspect presentation. Unity's Frame Timing Manager supports macOS Metal and Windows backends, but reports delayed timing data and has documented measurement caveats. Even `MTKView.preferredFramesPerSecond` is a preference chosen against display capabilities. [Godot profiler](https://docs.godotengine.org/en/stable/tutorials/scripting/debug/the_profiler.html), [Unity frame timing](https://docs.unity3d.com/6000.0/Documentation/Manual/frame-timing-manager.html), [MTKView frame-rate preference](https://developer.apple.com/documentation/metalkit/mtkview/preferredframespersecond)

Physical pad-to-sound and pad-to-pixel latency still require suitable hardware measurements. Keep those separate from software scheduling and frame-pacing results. If the spike fails, retain the working lesson and its portable core, document the failure, and test the next renderer against this same contract.
